# LogicMargin 0.4.0 性能优化

2026-11-03，基于 [0.3.0 基线](performance-baseline.md) 完成实现与复测。保留 Node 和现有存储格式，没有新增依赖。

## 实现

- 网页的 GET、POST 和长轮询使用 `?view=current`，只返回当前图／讨论、轮次目录、固定记录目录及提交匹配信息。初始自动加载本轮比较基线，其他原图和固定记录正文按需读取；最多缓存 6 张历史图。
- 不带参数的原完整接口、CLI、完整会话备份与固定记录下载保持原来的完整数据。历史图和记录分别通过 `GET /api/review-sessions/:id/snapshots/:round`、`GET /api/review-sessions/:id/records/:recordId` 读取。
- 服务端按会话串行写入，使用最多 16 个条目、64 MiB 序列化字节预算的 LRU 缓存。mtime、ctime、inode、size 检测外部更改；文件句柄与目标签名一致才缓存已写状态。缓存对外返回独立副本，不让调用者改写内部状态。
- 已验证的旧图和固定记录保持不可变，写入时复用；保留新输入及变更字段校验，减少整份历史的重复解析、深拷贝和 equality 序列化。写入失败不更新缓存，长轮询直接接收已提交状态。
- 编辑时缓存反馈统计、独立讨论列表渲染，画布建立对象／场景／批注索引，避免每个节点、连线重复扫描批注。保持历史只读、原位置、稳定编号、视口和选择行为。
- 静态资源启动时预压缩，API 超阈值异步 gzip，自动协商编码；保留 identity、HEAD、缓存头、Origin 校验及关闭授权。

没有为了精简数据取消 round/version 冲突检查、提交内容比对、离线恢复、固定提交包、原批注锚点或最终回复原子发布。当前图／讨论仍是完整同步，不是逐字段增量事件；同一次更新仍可能有 POST 与长轮询两个较小响应。

## 服务端复测

同一台 M4 Pro / 24 GiB / Node 26.13.0，本机回环，每操作 20 个正式样本，另 3 次预热。固定 42 节点、50 连线，R30 / 1000 条合成意见。

下表中 0.4 日常路径为 `view=current`，缓存已命中；0.3 每次都重新解析文件。首次读盘单独列出，不能把热路径当作冷启动。

| 操作，中位数 | 0.3.0 | 0.4.0 |
| --- | ---: | ---: |
| 读取当前会话 | 54.37 ms | 1.99 ms |
| 添加意见 | 134.90 ms | 13.86 ms |
| 提交并领取，2 个请求 | 277.86 ms | 26.19 ms |
| 原子发布新版及最终回应 | 151.78 ms | 28.44 ms |
| 写入至长轮询完整接收 | 193.14 ms | 27.91 ms |
| 当前接口响应体 | 10,424,310 B | 631,192 B |
| gzip 响应体 | 未启用 | 30,669 B |

0.4 当前读取 p95 为 2.19 ms；实际 gzip 读取中位数 3.94 ms、p95 4.20 ms。压缩数据是 raw HTTP 收到的正文长度，不包含 HTTP/TLS 开销，也不是跨设备 Tailscale 线路流量。合成批注具有重复文本，压缩率不能直接推及所有真实评审。

连续添加意见从 1000 增到 1023（含预热），没有通过外部改文件来重置缓存；约 2.3% 数据增长在输出里记录。提交、发布和轮询各样本使用原基线恢复并预热缓存，准备时间不计入延迟／CPU。旧完整接口另保留了每样本恢复文件的冷缓存测量。

多会话阻塞也改善：大会话写入期间，同进程小会话 GET 中位数由 131.95 ms 降至 6.11 ms。人工 25 ms 异步队列屏障下，无关读由 28.20 ms 降至 0.70 ms，确认队列不再跨会话拦截。共享事件循环的同步 CPU 阻塞仍存在。

## 浏览器复测

相同生产构建方式、Chrome 156、1440×900，无 CPU／网络限速，各场景 5 个样本。页面就绪和交互定义沿用基线，交互包含状态达成后的两个 animation frame。前端合成历史的文件大小和服务端轨迹不同，不跨表拼接成同一整轮耗时。

| 场景／指标，中位数 | 0.3.0 | 0.4.0 |
| --- | ---: | ---: |
| 魔灵秘境结构，R10 / 200 意见，保存回复至页面同步 | 120.8 ms | 66.6 ms |
| 单场景 200 节点 / 200 意见，保存回复至页面同步 | 174.3 ms | 100.8 ms |
| 单场景 1000 节点 / 1000 意见，首次画布就绪 | 783.6 ms | 343.2 ms |
| 同压力样本，打开批注列表 | 267.0 ms | 163.3 ms |
| 同压力样本，输入修改至两个 frame | 124.5 ms | 31.7 ms |
| 同压力样本，保存回复至页面同步 | 1396.0 ms | 498.9 ms |

0.4 最大样本第一个 context 的画布就绪为 569 ms，后续约 338–345 ms；浏览器 context 冷缓存不代表服务端缓存或磁盘冷缓存。缓存重载样本有波动（该场景约 283–425 ms），未宣称每一次操作都达到中位数。首次就绪以当前画布为界，不以全部按需历史下载完毕为界。

该前端大样本当前响应正文由约 20.57 MB 降至 1.10 MB，gzip 后约 41.9 KB；存储中的完整历史仍保留，没有通过删历史取得收益。

## 限制

首次读取 R30 当前视图仍约 48 ms，需要全文件解析。旧完整接口的强制冷读约 78 ms，较 0.3 的约 54 ms 更慢，原因包含保留独立结果副本的成本；不能说所有兼容路径都变快。

连续混合压力轨迹 RSS 仍可能达到约 0.8–0.96 GiB。缓存预算统计序列化字节，不是 RSS 承诺；此次没有证明大负载稳态内存已低或泄漏问题已解决。持久化仍整文件原子替换，未改成数据库。

大量节点／讨论仍挂载 DOM，未加入列表或画布虚拟化。最大前端样本保存回复仍约半秒；后续可在真实需求达到该规模时继续优化，先保证尺寸测量、原位置定位和讨论连续性。

未实测真实跨设备 Tailscale、实体手机、Windows/Linux 性能，也没有真实 Agent 读源、生成图、修改和回应的整轮计时。
