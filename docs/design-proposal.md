# LogicMargin 产品设计与操作流程提案

状态：操作流程与交互方案已获用户认可；本文保留初次设计，当前代理闭环与安装方式见 [代理评审流程](agent-workflow.md) 和 [agent 插件](agent-plugin.md)。

后续交互细化见 [交互优化提案](interaction-design.md)，保留本文已确认的操作流程与状态边界。

## 1. 产品定位

LogicMargin 让懂业务的人通过图检查规则、数据变化与执行顺序，并将意见交给开发者或代理处理。
策划、产品和运营可以完成业务判断；开发者按需展开源码与验证依据。
一轮评审应能回答：看的是哪版逻辑、提出了哪些问题、代理怎样处理、哪些结果已由人确认。

推荐形态是**可独立使用的网页＋轻量本地代理接入**。首版面向同一台机器上的单人评审。
网页负责阅读、批注、讨论与复核；代理负责核对源码、准备逻辑说明、处理意见和回传结果。
正式日常流程直接连接网页与代理，不要求用户反复搬运文件；文件导入导出保留为备份和开发验证方式。

初次方案落地时已实现：流程演示样例、流程图、节点/连线/组合及场景批注、共享编辑器、持久草稿、回复、固定意见包、逐条人工复核、整轮通过记录、文件交换与系统明暗主题。
当时通过文件交换意见与代理回应。现已接入持久会话、代理领取回执、回复、新版发布和服务自动启动；具体能力与边界以上述当前流程文档为准。

## 2. 如何参考 Crit

Crit 的源码核对和固定版本依据见 [Crit 参考方案](crit-reference.md)。下表右列为 LogicMargin 的设计建议。

| Crit 已核实机制 | LogicMargin 的对应设计 |
| --- | --- |
| 行、文件、整份评审均可批注 | 节点、连线、一组步骤、场景、整个评审均可批注 |
| 原评论下保存回复 | 同一意见下讨论规则、修改说明和异议，保留原始问题 |
| 保存评论与 Finish Review 分开 | 随时保存意见，明确点击“提交本轮意见”才交付处理 |
| 回复与 resolve 分开 | 代理返回处理结果，由人复核后确认解决 |
| 评审轮次与内容快照有独立记录 | 分开保存逻辑版本、源码依据和本轮意见，能回看当时审查的内容 |

## 3. 页面结构

保持克制的工具界面，自动跟随系统明暗外观。

| 位置 | 展示内容 | 主要操作 |
| --- | --- | --- |
| 顶栏 | 评审名称、逻辑版本、本轮状态、来源是否已核对 | 提交本轮意见、查看历史、导出备份 |
| 左侧 | 业务场景与章节、本轮待处理意见入口 | 切换场景、添加场景意见或整体意见 |
| 中间 | 当前场景的流程图及本次变化 | 看图、展开步骤、选节点/连线、框选、就地批注 |
| 右侧 | 选中步骤的规则和数据，或一条意见的完整讨论 | 查看细节、回复、复核、确认解决 |

图内弹窗负责快速写意见和阅读相关讨论；右侧面板适合持续阅读长讨论与版本对照。
打开任一处的同一条意见，都进入同一讨论，不复制出第二份批注。
小屏幕将场景目录收为选择器，细节与讨论放在画布下方；核心操作无需悬停才能发现。

内容分三层展开：

1. **场景总览**：例如“升级订阅套餐”“启用演示集成”“选择通知渠道”，先说明本场景做什么。
2. **业务步骤**：节点展示判断、动作、输入输出、数据前后变化、失败出口与副作用。
3. **核对依据**：按需展开对应源码、版本、测试依据和未核实项；不把路径和哈希铺在业务阅读面上。

“已有实现”和“希望改成的规则”明确区分：图说明已核对的现状，意见记录期望；代理返回新版后再展示结果。
未核对的描述要带文字提示，未展示范围可随时查看；不使用一个笼统可信度分数代替依据。

## 4. 批注对象与操作

| 对象 | 入口 | 适合表达的问题 |
| --- | --- | --- |
| 单个节点 | 节点批注按钮、右键 | 这个条件或数据变化有误 |
| 一条连线 | 选择后批注、右键或双击 | 进入下一步的条件不对、顺序不对 |
| 一组步骤 | 多选/框选后“批注所选” | 这几步共同产生问题、失败处理缺失 |
| 当前场景 | 场景菜单中的“场景意见” | 整段流程遗漏一个分支或边界情况 |
| 整份评审 | 顶栏或目录中的“整体意见” | 缺少一个业务场景、评审范围不完整 |

后两种对象已在首版加入，保证“图中缺少某件事”也能被评论，不必勉强挂到无关节点。
框选保存所选业务对象的身份集合；缩放、平移和重新排版不改变批注落点。
批注保留当时的对象名称、关键规则和所属版本，供对象被删除后回看。

编辑器只要求填写一段自然语言，提示“哪里不符合预期，希望怎样处理”，不强制填写多个表单字段。
输入草稿按目标保留；关闭编辑器后重新打开可继续，保存成功后才清空草稿。
点击“保存批注”产生本机记录；界面明确显示“已保存，尚未提交本轮”。
已提交的原意见保留当时正文，后续纠正或补充通过回复表达；未提交意见可以编辑。

## 5. 一轮完整操作

以下以虚构订阅工作区作为**设计演示**，规则依据见 [公开样例](sample-source.md)，不代表真实系统缺陷。

### 第一步：由代理准备本次评审

用户在开发对话里提出“用 LogicMargin 评审这次订阅设置改造”。
代理核对选定工作区和改动范围，准备场景图、源码快照、依据及尚未展示的范围，然后打开评审页。
页面首先展示评审范围和版本，用户能知道是在看当前实现、历史版本还是某个改造结果。

### 第二步：看懂逻辑，定位意见

用户打开“启用演示集成”，沿图查看套餐检查、额度检查、扣点和启用集成。
点击“启用集成”，看到执行前后的套餐、集成集合、通知渠道，以及失败出口。
需要确认依据时再展开源码或测试说明；不懂代码也能继续阅读规则与数据变化。

### 第三步：图上保存批注

用户框选“检查额度 → 扣点 → 启用集成”，填写：
“这里只启用集成，保留套餐和通知设置，不要自动更换通知渠道。”
保存后，选中流程出现批注标记，目录和讨论列表同步出现该意见，状态为“待处理”。
此时仍在本轮评审中，用户可以继续看其他场景，也可以对整个场景补充遗漏问题。

### 第四步：提交本轮意见

顶栏展示待提交意见数量，用户可先展开本轮范围、逻辑版本和意见汇总。
点击“提交本轮意见”后，固定本轮意见正文、对象上下文及对应版本，形成一份可追溯的提交记录。
存在未保存输入时，提示选择保存后提交或保留为草稿，不能默认丢弃。
后续本地新增意见进入下一轮草稿，不悄悄改写已交给代理的内容。
同一评审先只处理一个已提交轮次，期间可继续记草稿，避免多个代理处理轮次同时改动同一份逻辑。

接入通道将本轮意见交给代理：未收到回执时显示“已提交，等待代理接收”；有回执后才显示“代理已接收”。
文件验证阶段显示“已生成意见包”，需要实际交给代理后才进入后续处理，不能仅凭导出成功显示已接收。

### 第五步：代理回应并回传结果

代理针对每条意见返回处理说明：已调整什么、依据是什么、有哪些验证结果，或为什么认为不需要改动。
需要修改时，同时回传新版逻辑与对应源码快照，页面标出新增、变化和删除的步骤或条件。
意见下出现代理回复，进入“待复核”；回复本身不把意见标为已解决。
没有代码变化的解释也可以交给人复核；存在异议或信息不足时，原线程继续讨论，明确标注需澄清事项。

### 第六步：人工复核

用户点击一条待复核意见，看到原意见、代理说明、当时的逻辑片段和新版对应位置。
核对“集成集合新增、套餐保持、通知渠道保持”后，点击“确认解决”。
仍不符合期望时，点击“仍需调整”并补充说明，该意见回到待处理，可进入下一轮提交。
本轮全部意见已解决、用户确认本轮覆盖范围后，点击“通过本轮评审”，记录对这一版业务行为的确认。
本轮没有意见时，可以直接确认范围并通过当前版本，同样保存版本与确认记录。

## 6. 三种状态分开表达

**意见线程状态**回答“这条问题处理到哪里”：

| 状态 | 含义与下一步 |
| --- | --- |
| 待处理 | 已提出问题，等待回应或继续调整 |
| 待复核 | 已有处理结果或相关版本变化，等待人重新判断 |
| 已解决 | 人已确认；仍保留原意见、回复与确认时版本 |

**本轮状态**回答“这一批评审进行到哪里”：

| 状态 | 进入条件 |
| --- | --- |
| 评审中 | 正在阅读和整理本轮意见 |
| 已提交 | 本轮内容已固定，等待接收与处理 |
| 处理中 | 代理已确认开始处理 |
| 待复核 | 本轮处理结果已返回，等待人核查 |
| 已通过 | 人已确认本轮所审版本与范围 |

**交付提示**回答“内容实际上送到哪里”：本机已保存、已生成意见包、等待接收、代理确认接收、已返回结果。
交付失败时保留已提交内容和草稿，允许重试；重复接收同一提交或回复不产生重复意见。
“生成了文件”“代理回复了”“单条已解决”分别不能代替“代理接收”“本轮通过”和“新版已复核”。

## 7. 版本、过期与历史

- **逻辑版本**：用户正在阅读的场景、规则、数据变化和关系的固定内容。
- **源码快照**：准备该逻辑说明时核对的代码内容，包含未提交变化时也能区分。
- **评审轮次**：哪一批意见及其回应；一次轮次不能直接等同于一次 Git 提交。

查看历史轮次时还原当时的图与意见；切到新版时突出新增、修改和删除，并能从原意见跳到新版对象。
节点只是换位置时，意见继续挂在原对象上；对象消失时显示“原步骤已移除”，保留当时上下文，不按相邻坐标猜替代目标。
未解决意见继续按版本变化要求复核。已有人工确认记录的已解决意见，只在关联节点、连线、场景或评审范围的逻辑/代码依据变化，或出现新代理回复时重新待复核；无关版本、源码指纹变化及代码行号位移不会重开。
原确认版本与轮次始终保留，不将跨轮继承伪记为在新版重新确认。
回传结果先核对对应提交与版本；旧轮结果挂回原轮次，提示当前已有新版，由人选择查看或要求基于新版处理，不自动覆盖当前图。

本地接入可核对对应源文件是否变化：发现变化时提示“来源已变化”，用户仍可阅读和讨论历史图。
提交前可以更新到当前逻辑，或明确选择“针对历史版提交”；历史意见始终带其版本，不能显示为当前版验收。
无法核对来源时显示“尚未核对当前仓库”，不会将固定快照呈现为实时状态。
通过本轮仅记录用户对所展示版本和范围的业务确认，覆盖与未核实项仍随记录保留。

## 8. 接入方式与实施顺序

推荐由一份共用评审模型连接三个部分：网页评审界面、本地评审记录与交换通道、代理接入命令。
网页不绑定某一种代理；Codex/T3 等通过轻量接入层准备评审、读取本轮意见、写入回复和新版结果。
本地通道只管理本轮记录与消息交换，代码修改沿用代理已有的开发工作区流程。
插件后续可负责入口和自动打开网页；网页本身保持独立可用。

| 阶段 | 交付重点 | 验收结果 |
| --- | --- | --- |
| 先验证记录约定 | 固定提交、回复、版本关联与人工复核；文件交换作为开发验证方式 | 同一意见能完整走过提交、回应、新版复核，历史不被改写 |
| 正式首版接入 | 小型本地服务与轻量代理命令，共用上述记录约定 | 从代理发起到网页提交再到结果返回，日常不需手工搬文件 |
| 再扩展表达 | 时序图、状态图以及更精确的变化影响提示 | 同一套意见和历史记录可用于不同逻辑视图 |

首版保留：流程图、图内批注、场景/整体意见、讨论线程、一次提交、代理回传、新旧对照和人工复核。
首版不展开多人账号、跨机器协同、远程执行平台及全部代码 diff 界面。

## 9. 验收重点与待审阅决定

- 保存单条批注后仍可继续整理；只有提交动作才形成固定的一轮意见。
- 代理返回或重复返回结果，原意见不丢失、不重复，不会自动解决。
- 看旧图、收到过期结果、目标被删、处理失败时，页面能说明发生了什么，并保留可继续处理的记录。
- 切换主题、关闭编辑器、刷新网页后，已保存意见及正式设计中的输入草稿都可恢复。
- 非程序员能独立发现并表达“遗漏流程”和“数据变化不符合规则”，无需先理解源码路径或提交哈希。

用户已确认以下方向，首版按此实现；真实代理接入继续按后续阶段推进：
1. **独立网页＋本地代理通道**，让网页能单独使用，也让日常评审减少手工交接。
2. **逐条保存＋一次提交本轮**，给用户明确的思考阶段和交付边界。
3. **代理回应＋人工复核关闭**，由人确认业务结果，完整保留版本和讨论过程。
