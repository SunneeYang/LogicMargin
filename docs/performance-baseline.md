# LogicMargin 0.3.0 性能基线

测量日期：2026-11-03。结论：当前魔灵秘境规模的插件开销很小；轮次、批注和单场景节点增多后，全量会话传输、解析与前端重复计算成为明确的优化目标。目前没有更换 Node 技术栈的性能依据。

## 验证范围

自动化已经覆盖“保存意见 → 提交本轮 → Agent 领取 → 发布新图和最终回复 → 人工复核／通过 → 重启恢复”的技术闭环。真实魔灵秘境会话仍为 R1、0 条意见，尚未完成真实人工反馈驱动的一整轮修改。

本次没有测量 Agent 读取代码、理解需求、生成流程图、修改代码／文档、撰写回应的真实时间，也没有测量人的阅读时间。它们不能用服务端 API 延迟替代。当前不能确认它们占整轮耗时的比例。

## 环境和方法

- Apple M4 Pro，12 个逻辑 CPU，24 GiB 内存；macOS 27 arm64，Node 26.13.0。
- 前端为生产构建，Chrome 156.0.8078.75，无 CPU／网络限速，1440×900。首次加载使用新浏览器 context，HTTP 缓存为空；这不等于重启电脑后的磁盘／进程冷缓存。
- 服务端在独立子进程、随机回环端口、隔离数据目录运行；延迟包括请求发出至完整响应体收到，不包含 driver 的 JSON 解析。20 次正式样本，另有 3 次预热。CPU/RSS 只统计服务端子进程。
- 前端每场景 5 次首次加载与缓存重载；正文主要报告中位数。交互计时从 DOM 操作开始，到状态达成后两个 animation frame，包含帧等待；并非单独的 JavaScript 执行时间。输入各测 3 次，共 15 个样本。
- CLI 大部分测量为 12 次正式样本、2 次预热；后台启动和受控事件各 5 次。文件系统缓存为已预热或未受控状态。
- 服务端、CLI、浏览器的主要 CPU 采样先后运行，避免互相竞争。未测试真实跨设备 Tailscale 链路、低性能手机、Windows/Linux 或多用户容量。
- 不修改产品实现、真实评审或游戏源码。所有写操作针对临时副本，结束后删除临时目录；0.3.0 原始基线冻结在忽略目录 `artifacts/performance/baseline-0.3.0/`；重新运行脚本测量当前工作树。

## 服务端

固定魔灵秘境 42 节点、50 连线、5 场景，使用真实 API 搭建不同轮数／意见数的合成评审轨迹。文件摘要仅是性能 fixture，不是重新验证 Vast 业务语义。

以下均为中位数 / p95，单位 ms：

| 轮次 / 意见数 | 完整会话字节数 | 读取会话 | 保存批注 | 提交并领取 | 原子发布新版 | 写入至等待者收到更新 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| R1 / 5 | 104,102 | 0.80 / 0.99 | 2.14 / 2.68 | 4.84 / 5.20 | 3.89 / 5.26 | 4.41 / 5.65 |
| R10 / 200 | 1,611,802 | 9.34 / 10.03 | 22.16 / 25.35 | 49.09 / 54.33 | 26.31 / 27.79 | 31.55 / 34.67 |
| R30 / 1000 | 10,424,310 | 54.37 / 57.85 | 134.90 / 146.52 | 277.86 / 295.62 | 151.78 / 159.78 | 193.14 / 199.90 |

“提交并领取”是两个 HTTP 请求；原子发布包含新图和最终回应。轮询列从写请求发出开始，包含服务端处理、全量状态读取／序列化及本机传输，不含事先注册等待。25 秒只是长轮询上限，不是每次通知要等 25 秒。

在 R30 样本中，一次批注 POST 返回约 10.42 MB，已注册的一个长轮询也返回约 10.42 MB：同一次更新的服务端到客户端响应体合计约 20.85 MB。这是两个响应的正文计数，不含 HTTP/TLS，也不等于实测 Tailscale 线路流量。

大评审写入时，同一服务内另一个独立小评审的 GET 中位数从正常约 0.8 ms 上升到 132 ms；放到另一服务进程的对照为 1.22 ms。另用 25 ms 的人工空闲队列屏障，将无关读取从 1.13 ms 推到 28.20 ms，确认全局 serial 队列会阻塞其他会话。实际 HTTP 延迟同时受共享事件循环的同步 CPU 影响，不能全部归因于队列。

额外 CPU 采样中，主要时间落在全量 JSON 解析、`serializeReview` 的格式化序列化／UTF-8 大小检查、`structuredClone`、全量 equality 序列化及 GC，而非只有文件写入。对应实现见 [SessionStore](../server/session-store.ts)、[模型校验](../src/model.ts)、[API 响应](../server/api.ts)。

小样本服务端采样 RSS 约 61–64 MiB；R30 连续压力轨迹中的采样 RSS 峰值最高约 1.12 GiB。这不是单次请求新增内存、稳态占用或泄漏证明。真实已安装服务在测量末尾的单次空闲观察约 48 MiB、CPU 0%，同样不代表长期平均值。

## 浏览器

第一行使用真实流程结构和原始正文副本。其余为合成批注／历史；最后两行额外使用合成单场景链。前端压力 fixture 的历史保留方式与服务端轨迹不同，应按字节数理解负载，不能直接把两张表同样的“R10 / 200”视作同一数据量。

以下为本机中位数，单位 ms：

| 场景 | API 完整会话字节数 | 初始场景节点数 | 首次画布就绪 | 缓存重载 | 打开批注列表 | 切修改前 / 当前 | 保存回复至同步完成 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 魔灵秘境 R1，0 意见 | 97,950 | 9（全图 42） | 109.5 | 80.0 | 31.9 | — | — |
| 魔灵秘境结构 R10，200 意见 | 2,841,941 | 9（全图 42） | 152.3 | 130.2 | 39.2 | 59.0 / 66.3 | 120.8 |
| 合成 R10，200 节点／200 意见 | 4,128,861 | 200 | 202.6 | 147.2 | 40.5 | 75.1 / 82.5 | 174.3 |
| 合成 R10，1000 节点／1000 意见 | 20,571,801 | 1000 | 783.6 | 763.9 | 267.0 | 379.0 / 350.6 | 1396.0 |

保存回复包括浏览器计算、API、长轮询和最终渲染，不能当作服务器的单接口时间，更不包括 Agent 撰写回复。每次浏览器样本会增加一条短回复；5 次样本的微小累计增量不足 1 KiB，仅当前图变化，历史不变。

输入修改至两个 frame 的中位数：两种 200 意见样本约 32 ms；1000 节点／1000 意见样本约 125 ms。后者可观察到长任务，界面 DOM 约 4.2 万个元素，已经有可感知的输入迟滞。魔灵秘境初始页面 DOM 约 477 个元素。

源码中的候选原因需要在优化后逐项复测：

- [App](../src/App.tsx) 在编辑器每次输入时重新执行 `pendingFeedback`，并重建讨论列表；即使讨论正文被 `hidden` 隐藏仍参与 React 渲染。
- [画布](../src/GraphCanvas.tsx) 为每个节点／连线扫描评论，全量场景节点均挂载。可以预先建立目标到评论数量的索引，减少重复查找。
- 当前 UI 收到每次变动后，都会重新校验完整历史。历史快照不可变，适合按发布版本加载和复用。

## CLI、来源核验与网络

| 操作 | 中位耗时 |
| --- | ---: |
| 新 Node 空进程 | 76.0 ms |
| 分发包 `--help` | 93.7 ms |
| 分发包 `get`，37,750 B 的回环 stub 响应 | 99.8 ms |
| 已运行进程内 `runCli get`，同一 stub | 0.65 ms |
| 后台服务已停止后启动，包含新 CLI 进程 | 195.3 ms |
| 已有后台服务复用，包含新 CLI 进程 | 99.8 ms |
| 1 MiB 单文件的完整来源核验 | 0.68 ms |
| 16 MiB / 2 文件的完整来源核验 | 9.76 ms |
| 1 MiB / 128 小文件的完整来源核验 | 7.38 ms |
| 分发包进程内完成上述 16 MiB `verify` | 104.5 ms |

`get` 使用 GET-only stub 分离进程／CLI 成本；不能把它当作大历史会话的真实服务处理时间。源文件为合法大小内的 UTF-8 合成数据，包含片段核验。纯 SHA-256 分别约 0.35 ms / 1 MiB、4.87 ms / 16 MiB；128 小文件比同字节的单文件更慢，说明路径解析和逐文件 I/O 也要考虑。

当前托管服务对 JS 和 API 均未启用 HTTP 内容压缩。对真实在用响应离线计算 gzip 大小：

| 资源 | 当前原始字节 | gzip 后字节（仅估算） | 体积减少 |
| --- | ---: | ---: | ---: |
| JS bundle | 519,682 | 161,445 | 68.9% |
| 真实 R1 完整会话 | 97,962 | 29,128 | 70.3% |

这不是已经交付的压缩收益；重复历史通常还会有更高压缩率，但未测。静态资源已有长期缓存，所以压缩 JS 主要帮助首次加载；API 每次全量返回的压缩／精简更关系持续使用。

## 优化次序

1. **先减少同步数据量。** 将日常当前图／线程更新与完整历史分开，历史按轮次按需读取；批注 POST 不再同时返回整个会话。保留明确的 round/version、冲突检测、离线恢复和原子发布，不用精简响应来弱化一致性。增加版本化 API 或兼容期，避免破坏已安装 agent。
2. **减少全量复制、解析和序列化。** 首次读盘及写入边界保持校验；不可变历史不必随每条回复重新格式化、深拷贝、对全对象做 JSON equality。单服务持有数据目录的约束可帮助安全缓存，但恢复／外部改动仍要明确处理。队列可按 session 隔离；它本身不能解决大同步 CPU 阻塞。
3. **优化前端输入与大列表。** 缓存仅由 review/history 决定的反馈统计；隔离编辑器状态；目标评论计数建索引；需要时对长讨论列表做虚拟化。画布按视口挂载要同步解决节点尺寸测量、适配视图及原位置定位，不能直接打开一个开关就视为完成。
4. **给静态资产与 API 加合适的压缩。** 静态文件可预压缩；动态 API 的压缩阈值／CPU 成本需测，精简响应优先于压缩冗余数据。对 Tailscale 的实际改善需跨设备验证。
5. **再测 Agent 工作本身。** 下一次真实评审记录读源、图生成、代码修改、回应、发布校验和 UI 就绪的独立时间；沿用稳定对象 ID 和已有图做局部修改，批量交回最终回复。由真实数据决定是否需要新增自动排版或生成工具，不为目前约 0.1 秒的 CLI 开销换栈。

本次只建立基线和优化建议，没有改变服务协议、渲染实现或重新部署。
