# 每轮流程更新、变化对照与批注定位

状态：2026-11-03 首版已实现。下表记录实施前 `f9a983f` 的问题，后文保留设计约定；拆分／合并关联编辑、更多历史选择和宽屏并排尚未实现。

目标：人每轮复核时看到明确对应本轮修改的流程，能看出变化，并能找到旧意见的原位置。代理回复、发布新版和人工确认解决分别表达。

## 实施前行为与缺口

| 已核实的当前行为 | 对这次需求的影响 |
| --- | --- |
| [会话模型](../src/session-types.ts) 和 [会话存储](../server/session-store.ts) 保存每轮发布时的流程快照、固定提交记录及当前评论。 | 已有历史图基础，无需重新设计一套存储。 |
| `SessionStore.revise` 校验并发版本、评审 ID 与轮数，再合并并开轮；相同旧图也可以原样发布。 | 轮次增加不能证明内容已经同步修改。 |
| [CLI](../bin/logic-margin.ts) 的 `revise` 读取 JSON 后发送；[模型校验](../src/model.ts) 接受文本指纹和摘要，不重算源文件。 | 更换版本字符串或指纹不能作为来源已更新的证据。 |
| 代理回复立即触发 `needs-review`，但回复本身不更新图。 | 人可能在新版尚未发布时，对着旧图确认代理的修改。 |
| `rebaseReview` 保留原意见和回复，目标消失后保留评论；同评论 ID 改写原目标会冲突。 | 可以避免丢意见，但缺少“保留原锚点，同时关联新版位置”的表达。 |
| [页面](../src/App.tsx) 只渲染当前图；变化相对内存中的上一份图计算。 | 刷新后对照基线可能丢失，无法稳定回看原图。 |
| [画布](../src/GraphCanvas.tsx) 对新增、修改节点使用同一种标记，移除目标没有图形可点。 | 当前提示不足以展示本轮具体改了哪里，连线变化也需要补足。 |

以上是本工程事实；用户描述的 Crit 经历作为需求背景，不推断 Crit 所有版本均存在同样问题。

## 已采用的交互

采用**单画布的“修改前 / 当前”切换、固定基线的变更清单、可追溯的历史批注**。默认当前图。

- 在现有紧凑工具栏加入 `修改前 R2 | 当前 R3`，显示当前查看的图版本。竖向流程继续使用完整画布，不默认增加两张并排图。
- “本轮变化”按需展开，列出新增、修改、删除的节点和连线。点新增项看当前图，点删除项看修改前图。
- 变化详情说明规则、条件、输入输出的前后差别；源码依据更新单独标注，纯排版不算逻辑变化。
- 每个场景、版本记住视口；同一业务对象跨版本尽量保持阅读位置。版本切换保留正在查看的讨论线程，不每次缩放整张图。
- 历史图明确标为只读。新增批注、确认解决与整轮通过针对当前发布版本执行。
- 宽屏并排对照可以后加；首版先把单画布切换与定位做完整。

默认“修改前”应指**本次代理实际处理的固定意见包所对应的图**，由发布记录保存基线引用，不能临时用浏览器上一帧或推测的 Git HEAD。某条评论的“提出时流程”可能更早，提供独立入口；例如当前 R3 的意见仍可能要回到 R1 才能看见原目标。

## 代理交回一轮的约定

扩展现有 `revise`，以一次完整发布交回可复核结果：新版流程、来源清单和摘要、最终回应、必要的位置关联建议与变更说明一起校验、保存。

1. 人提交固定意见包；代理领取后进入处理中。
2. 代理可以先交流与回复，但页面仍显示“修改中／新版尚未发布”，保留正在审查的旧图，不能将回复当作新版完成信号。
3. 代理完成修改后，在明确的来源工作区重算受覆盖源码、文档及图内依据的摘要，整理实际流程；不会仅靠换 revision 表示同步。
4. 发布通过后，原子保存新快照、回应和关联记录，再切换为“新版可复核”。部分失败时保留上一份完整发布，避免新回复配旧图。
5. 人查看新图、变化和回应，再确认解决或继续提出意见。确认必须绑定当前图版本，不能在历史图或代理处理中确认尚未发布的修改。

来源检查在 agent 所在工作区进行；服务端校验发布数据的自洽性，不假装能读取远端 agent 的磁盘。读取范围由明确的来源工作区及受覆盖文件清单决定，不能由任意 JSON 路径扩大。

对“源码变了、图未变”分情况处理：

- 旧摘要或依据与实际文件不符：拒绝发布。
- 规则、条件、输入输出确有变化：代理必须更新对应图内容，发布时给出本轮变化与受影响意见。
- 格式、注释或图未覆盖的实现变化：允许声明“流程未变”，但要说明原因与覆盖范围，页面如实展示“源码／文档更新，流程无变化”。
- 只有说明、没有修改：允许明确的说明轮，保留原图与真实源指纹，不能伪造逻辑变化。

摘要核验只证明图内依据与给定文件版本对应，不能自动证明图已完整、正确地解释代码语义；这仍由 agent 整理与人的对照复核共同完成。

## 原批注与新版位置

评论线程身份、原始意见、提出时图版本和原目标保持不变；新版位置作为独立关联记录，不覆盖原目标。

| 流程变化 | 建议处理 |
| --- | --- |
| 同一业务步骤改名、移动，ID 保持 | 继续定位同一对象；显示其规则变化。排版位置不作为锚点。 |
| 多目标意见只有部分目标仍在 | 明确显示仍可定位和已移除的目标数量；可分别看当前和原位置。 |
| 原步骤被删除 | 讨论列表保留意见，显示“原目标已移除”，提供“查看提出时流程”。不默认删除评论或确认解决。 |
| 一个步骤拆成多个，或多个合为一个 | agent 可给出关联目标和原因，人可以核对、接受或调整；允许一对多、多对一。 |
| 没有可靠对应位置 | 保留为“待定位／仅在原版本查看”，用户仍能讨论和复核，不按屏幕距离或相似标题强行搬迁。 |

例如 R1 的“提交时消耗额度”在 R2 被移除、消耗移到保存输出阶段：原意见仍锚定 R1 的原步骤；当前卡片显示原目标移除、代理回应及建议的新版保存位置。人可切回 R1 看原位置，再看当前保存逻辑与差异，最后确认原问题是否解决。此例为虚构设计，只说明交互。

首版即使暂不支持手工编辑关联，也必须完成“列表保留 + 原图原位置”。这比不可靠的自动重挂更适合作为第一步。

## 历史图与评论数据的组合

不能直接渲染 `snapshots[旧轮次].review.comments` 就认为恢复了全部批注：快照是在开轮时冻结的，之后写入的意见并不在其中。

推荐把以下内容分开：

- 不可变的图快照，以及本次发布实际基于哪张图。
- 当前持续更新的评论线程，以及不变的提出时图版本和原锚点。
- 每个发布版本上的定位结果，包括未能定位、部分移除或人工接受的关联。
- 人提交当时的固定意见包，供查看“当时提交了什么”。

查看历史图时，使用冻结的图内容，叠加适用于该版本的批注锚点；讨论栏明确显示当前处理状态。需要查看当时提交记录时，才显示固定意见包中的历史正文和状态。

图快照要有稳定发布身份，可在会话中使用明确的轮次引用；评论当前只有 `revision`，不足以区分同一源码版本被多轮复用的情况。提出版本、定位版本、人工复核版本都应指向明确发布，不能只依赖任意版本字符串或时间戳。

变化由选定的两份固定图快照计算。现有 `getChanges` 可以复用，但要区分业务语义、源码依据和排版变化。对照不依赖浏览器内存，刷新、重连和服务重启后保持一致。

## 实施优先级与验收

第一版作为一个完整闭环交付：

1. 发布校验与阶段约束：交流回复不冒充新版就绪，最终回应与新版图一起发布；明确来源及“流程未变”的例外。
2. 单画布前后切换与持久比较基线：新增、修改、删除可定位，节点和连线均覆盖。
3. 历史批注投影：原图可见原位置，删除目标仍可从列表查看，当前确认绑定当前图版本。

后续再加拆分／合并关联的编辑与确认、更多历史版本选择和宽屏并排，不先做通用自动语义匹配或实时仓库监听。

至少验证以下场景：

- 只回复、尚未发布时，仍明确显示旧图和处理中状态，不能将旧图当作修改结果确认。
- 改代码或文档后发布旧摘要被拒绝；无流程变化时要求并显示原因。
- 条件或数据变化能看出前后差别；纯坐标调整不冒充逻辑修改。
- 删除节点或连线后原意见仍能跳到提出时快照；多目标部分删除能分别核对。
- 拆分、合并不会自动改写原锚点，也不会自动解决意见。
- R1 的意见在 R3 仍能回看 R1，同 revision 多轮也不串批注。
- 刷新、断线、重启后比较基线、当前图和讨论一致；切换视图保留线程与阅读位置。
- 发布失败、并发新评论或源码再次变化时，不生成回复、图和定位彼此不一致的半轮结果。

首版实现：CLI 先核验实际文件与片段摘要，发布必须提供实际处理的 `--base-round` 和 `--summary`；最终回应通过 `--replies-file` 与图原子发布。服务端保存固定比较基线、评论提出轮次、回复轮次和人工复核轮次。R2 起批注写入必须携带当前轮次，旧版离线队列若无法确定轮次会暂停并保留导出。

界面默认当前流程，提供修改前切换、本轮变化清单与字段对照；删除目标的讨论保留，能回到提出时原图。历史图只读，讨论显示当前处理状态；旧会话无法精确确定的原位置会明确标为推断。来源校验、阶段门禁、跨轮历史投影及浏览器操作已加入自动回归。
